Bug
1_resolve_profile encore importé dans personalization.py

Malgré le patch du point #6, personalization.py importe toujours _resolve_profile (privé) au lieu de resolve_profile. L'alias de compat masque le bug mais le couplage interne persiste.

Bug silencieux
2logger non défini dans cycle_engine.py

cycle_engine.py utilise logger.debug() (ligne 98) sans jamais importer ni instancier logging. En production, toute exception dans le calcul de nutrition cycle lèverait un NameError plutôt que de se dégrader silencieusement.

cycle_engine.py · ligne 98 (manque logger = logging.getLogger(__name__))

Feature morte
3has_cycle détecté mais jamais utilisé dans le pipeline

UserContext.has_cycle est calculé dans personalization.py et exposé dans les méta de orchestrator.py, mais aucune étape du pipeline n'appelle cycle_engine.adjust_ranking(). Le cycle féminin n'influence donc jamais le classement des recettes.

reco_engine/orchestrator.py · pipeline étape 6 manquante

Bug / incohérence
4graph_engine._load_graph utilise @lru_cache statique

_load_graph() est décoré @lru_cache mais le graphe d'ingrédients peut être mis à jour par culinary_product_engine. Contrairement aux autres loaders critiques (migrés vers _MtimeCache), ce cache ne s'invalide jamais sans redémarrage.

graph_engine.py · ligne 39

Dette technique
5graph_engine et learning_engine pas encore migrés

Ces deux modules sont explicitement marqués # conservé — pas encore migré dans les routes et le pipeline. Ils sont importés inline à chaque appel HTTP. Bloquer la migration étape 4 complète jusqu'à leur déplacement dans les sous-packages appropriés.

routes/recipes.py · pipeline.py · reco_engine/scoring.py

Duplication logique
6Double calcul de nutrition dans _compute_enrichment

Dans routes/recipes.py, _compute_enrichment() appelle load_nutrition_graph() puis score_recipe() qui recharge lui-même le même graphe via quality.py. Deux accès disque/cache distincts pour les mêmes données à chaque appel GET /recettes/{id}.

routes/recipes.py · _compute_enrichment · lignes 184–234

Robustesse
7pipeline.run() : imports inline dans la boucle principale

Les imports from backend.engine... dans run() sont à l'intérieur de la fonction (pas dans la boucle, mais rechargés à chaque appel de run()). Pour un pipeline appelé en batch, monter ces imports en tête de module détecte les erreurs d'import au démarrage et non à l'exécution.

pipeline.py · lignes 70–79

Qualité
8score_nutrition_values — logique de scoring dupliquée

nutrition_engine.score_nutrition_values() implémente son propre système de points (protein × 0.4, fiber × 0.3…) indépendamment de score_engine.quality._d_nutrition() et de ajr.ajr_score(). Trois calculs nutritionnels distincts sans source de vérité.

nutrition_engine.py · ligne 233 vs score_engine/quality.py vs score_engine/ajr.py

Amélioration
9explainer.py sans seuils configurables

Les seuils hi et lo de _DIM_RULES sont des littéraux hardcodés (7.5, 4.0…). Si les poids ou l'échelle du scoring changent, les labels resteront corrects mais les seuils seront silencieusement faux. Externaliser vers config.py ou en constantes nommées.

score_engine/explainer.py · _DIM_RULES

Amélioration
10Pas de test d'intégration pour le pipeline de recommandation

L'orchestrateur (recommend()) assemble 6 étapes sans aucun test de bout-en-bout vérifiant que le résultat contient bien final_score, profile_used, et timing_ms. Les tests existants couvrent les moteurs unitairement mais pas le pipeline complet.

reco_engine/orchestrator.py · aucun test d'intégration
